# 自動更新の仕組み（段階1）

作成日: 2026-09-03。実装指示書 §4 の具体化。

## 何が動くか

`.github/workflows/update.yml` が GitHub Actions で **毎日 06:00 UTC（日本時間 15:00）、11〜3 月のみ** 動く。
手動実行（workflow_dispatch）もできる。手順は次のとおり。

1. `python -m etl.fis_fetch --check-new --download --pdf-root source_pdfs`
   - FIS のカレンダー（区分 WC / WSC / OWG、種目 MO、対象シーズン）→ 大会詳細ページ → 添付 PDF、の順にたどる。
   - モーグル単走の「Results - Qualification / Qualification Run 1 / Qualification Run 2 / Final Run 1 / Final Run 2」
     だけを対象にし、`source_pdfs/<季節フォルダ>/<会場>/<会場>_<男子|女子>モーグル<ラウンド>_<codex>.pdf` に無いものを取得する。
     命名は `全試合のリザルト` と同じなので、そのままコピーしても整合する。
   - デュアルモーグル、スタートリスト、総合サマリー（"Results - Final"）、スタンディングは取得しない。
   - リクエスト間は 1.5 秒空ける（環境変数 `FIS_FETCH_DELAY` で変更可）。
2. 新しい PDF が 0 件ならそこで終了（PR も Issue も作らない）。
3. `python -m etl.build` を実行（読み取り A/B → 多層照合 → 公開ゲート → `data/` 出力）。
4. 結果で分岐する。
   - **全部緑**（`etl.build` が終了コード 0）→ `auto/results-<日付>` ブランチから
     Pull Request「新しいリザルト <日付>」を作る。本文に取得した PDF 一覧と `docs/検証レポート.md`。
   - **赤がある** → Issue「検証に失敗したリザルト <日付>」を作る。本文は同じ。PR は作らない。
   - PDF は取れなかったが取得エラーがあった → Issue「FIS からの取得でエラー <日付>」。
5. ログ（`.fetch/`）は Actions の artifact として 14 日残す。

## 人がやること

| 状況 | やること |
|---|---|
| PR が来た | 本文の検証レポートを見て、`data/` の差分が妥当ならマージする。マージ＝公開（GitHub Pages）。 |
| Issue「検証に失敗」が来た | レポートの赤い層を読む。PDF のレイアウト変更ならパーサを直す。FIS 側の誤植なら `--accept-revision` 等で通す。直したら手動実行（Actions → Run workflow）。 |
| Issue「取得でエラー」が来た | FIS の URL 構造変更か、Actions からのアクセス拒否。`etl/fis_fetch.py` 冒頭の URL 構造メモと突き合わせる。 |
| シーズン外に取り直したい | Actions → Run workflow で `season`（例 2026）と `categories` を指定。 |

段階2（全自動公開）は 1 シーズン運用後に、PR 作成をマージに置き換えるだけで切り替えられる。

## ローカルでの使い方

```
python -m etl.fis_fetch --season 2025 --category WC --list
python -m etl.fis_fetch --season 2025 --category WC,WSC --check-new --pdf-root "D:\Claude\ジャッジ分析\全試合のリザルト"
python -m etl.fis_fetch --season 2026 --category OWG --check-new --download --pdf-root source_pdfs --report fetch_report.json
python -m etl.fis_fetch --season 2025 --html-results "https://www.fis-ski.com/DB/general/results.html?sectorcode=FS&raceid=17202"
```

`--season` は seasoncode（シーズン終了年。2024-25 なら 2025）。

## 確認済みのこと（2026-09-03、この PC から）

- 2024-25 WC: 単走 19 レース、リザルト PDF 51 本を発見。ローカル `全試合のリザルト` と突き合わせて欠落 0。
- 2024-25 WSC（Engadin）6 本、2025-26 OWG（Milano Cortina）8 本、2025-26 WC 27 本も欠落 0。
- Engadin の 6 本を実際にダウンロードし、ローカルの PDF と SHA-256 が全て一致。
- FIS の HTML 結果表は「1 選手 1 得点（最後に滑ったラウンドの点）」のみ。第5層の外部照合は最終順位とこの得点だけ。

## まだ分かっていないこと

- **GitHub Actions から FIS に到達できるか未確認。** この PC からは 200 だが、FIS はデータセンター IP を弾くことがある。
  初回の手動実行で確認する。弾かれた場合は Issue「取得でエラー」が立つので、そこで対処を考える
  （UA 変更、間隔を延ばす、self-hosted runner など）。
- `etl.build` はまだ無い。ワークフローは「終了コード 0 = 全部緑、`docs/検証レポート.md` を書く」前提で組んである。
- 添付 PDF の種別名（`data-ga-download`）が FIS 側で変わると発見できなくなる。
  対応表は `etl/fis_fetch.py` の `RESULT_TITLE_TO_ROUND`。
- 会場名が FIS とローカルで違う場合の対応表 `VENUE_FOLDER_ALIASES`（今は "Waterville Valley Resort" → "Waterville" のみ）。
  ローカル検索は codex で行うので欠落判定には影響しないが、新規保存先のフォルダ名に影響する。


## 定期実行は無効（2026-09-03）

ChatGPT レビューの指摘で、FIS サイトの利用規約が自動取得（scraping）を制限している可能性が分かった。FIS または所属連盟経由で取得・加工利用の可否を確認するまで、`update.yml` の `schedule` はコメントアウトしている。手動実行（workflow_dispatch）と、手元での `python -m etl.fis_fetch` は可能だが、同じ確認事項の対象になる。


ワークフローファイルは `.github/workflows_disabled/update.yml` に置いてある（GitHub Actions は `.github/workflows/` 以下しか読まないので、この場所では動かない）。使うときは `.github/workflows/` へ移す。移すには GitHub のトークンに workflow 権限が要る（`gh auth refresh -s workflow`）。
