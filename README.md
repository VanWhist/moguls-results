## 1. 大会が増えたときにやること

### まず Claude Code にこう頼んでください

`D:\Claude\ジャッジ分析\moguls-results` で Claude Code を起動して、そのまま貼り付けてください。

> `README.md` の「1. 大会が増えたときにやること」を読んで、
> `全試合のリザルト\` に追加した ○○大会（YYYY-MM-DD）を取り込んでください。
> ETL を回して、検証レポートの結果を見せてください。内容を確認するまで push はしないでください。

**Van さんがやるのは「PDF を置く」「結果を見て公開の可否を決める」の2つだけです。**
自動更新（GitHub Actions）は用意してありますが、FIS サイトの利用条件（自動取得の可否）を確認するまで定期実行は無効です。手動実行（Actions の Run workflow）で PDF 取り込みと検証を行い、緑なら Pull Request が届きます（`docs/自動更新の仕組み.md`）。

### ステップ1: PDF を置く

`全試合のリザルト\<シーズン>\<会場>\` に、FIS の PDF を次の名前で置きます。

```
<会場>_<男子|女子>モーグル<予選|予選1|予選2|決勝1|決勝2>_<codex>.pdf
```

PDF は FIS の大会ページからブラウザで保存します（FIS の利用規約が自動取得を禁じているため、スクリプトによる一括取得は使いません）。Claude Code に Chrome を操作させて保存しても構いません。2026-27 の日程と保存先は `docs/大会予定_2026-27.md`。
デュアルモーグルは対象外です（置いてあっても無視します）。

### ステップ2: ETL を回す

```bash
cd D:\Claude\ジャッジ分析\moguls-results
python -m etl.build
```

最後にこの行が出ます（3〜4分）。

```
4413 records / 24 warnings / 0 errors / 公開対象 192/192 ラウンド
data/ を書き出しました: events 37 / rounds 192 / runs 4413 / athletes 241 / dataVersion 2026-09-03-0540
```

### ステップ3: この3つだけ見てください

**① `errors` が 0 か**

| | 意味 | どうするか |
|---|---|---|
| `errors: 0` | 問題なし | 次へ |
| `errors: 1以上` | **その大会は公開されない**（大会単位で全か無か） | `docs/検証レポート.md` のエラー節を Claude Code に見せて直してもらう |

`warnings` は 0 でなくて構いません。人が見て判断するものの置き場です（欠場、シード直接進出、氏名の表記ゆれなど）。

**② 新しいラウンドが取り込まれたか**

新しい大会は警告にこう出ます。

```
[layer0] 2026-27-8123-Q: 新しいラウンド（54 名）。内容確認後 `--accept-rounds` で基準に登録
```

画面で中身を確認したら基準に登録します。次回以降、登録済みラウンドの人数が変わるとエラーになります（取りこぼし・二重取り込みの検知）。

```bash
python -m etl.build --accept-rounds
```

**③ 公開済みの PDF が差し替わっていないか**

FIS が同じ大会の PDF を訂正した場合、こう出て公開が止まります。

```
[gate] 2026-27-8123-Q: 公開済みラウンドの元 PDF が変わった。内容確認後 `--accept-revision`
```

差分を確認して問題なければ `python -m etl.build --accept-revision`。

### ステップ4: 手元で画面を見る

```bash
python -m http.server 8765
```

ブラウザで `http://localhost:8765/` を開きます（HTML をダブルクリックしても動きません）。
新しい大会の選手を1人検索して、選手ページの「上のラインとの差」まで開いてみてください。

### ステップ5: Excel も作り直す（任意）

`全試合のリザルト_Excel` はデータベースから書き出す控えです。分析用に Excel が要るときは、公開後に次を実行します（3 分ほど。Excel で再計算してデータベースと全セル照合します）。

```bash
python -m etl.export_xlsx
```

以前の「PDF → Excel の3段階チェック」は使いません。この書き出しの方が検証が厚く、データベースと必ず同じ内容になります。

### ステップ6: 公開する

```bash
git add -A
git commit -m "2027-01-10 Ruka を追加"
git push
```

## 2. 検証の仕組み（多層照合）

数字の誤りが1つでもあると信頼を失うので、公開前に互いに独立な方法で同じ答えに辿り着いたときだけ公開します。

| 層 | 何を確かめるか |
|---|---|
| 第0層 完全性 | 出走数 = 抽出人数、登録済みラウンドの人数、run_id の重複、ペースタイムの有無 |
| 第1層 二重読み取り | 座標ベースのパーサ A と行テキストのパーサ B が全項目で一致 |
| 第2層 再計算 | FIS 規則（切り捨て、エア上限、最高最低除外、ターン下限、タイム点式）で合計を再計算し印字と一致 |
| 第3層 再構成 | ラン得点とタイブレークから順位を作り直し印字順位と一致。F1・F2 の出場者が前ラウンドの通過者と一致（フォーマット別） |
| 第4層 横断整合 | FIS コード → 生年の一貫性。氏名・国の変化は別名・履歴として警告 |
| 第5層 外部照合 | FIS サイトの HTML 結果と最終順位・最終ラウンド得点を突き合わせ（`--fis`、要ネットワーク）。照合できた大会数が期待数と一致しないと赤。FIS 側に PDF が無い既知の欠落は `upstream_missing` として緑と区別 |
| 正解データ | `golden/` の目視正解（PDF を画像で読んだもの）と一致 |
| 変異テスト | `python -m etl.tests.test_mutations` で、わざと壊したデータを各層が止めることを確認 |

公開ゲート: 1ラウンドでも赤があればその大会は出力しない。「検証が実行された件数 = 期待件数」も条件（0件照合で緑にならない）。公開済みラウンドの JSON ハッシュと元 PDF の SHA-256 を `etl/published_hashes.json` に記録。

## 3. 規則の版（26/27 の改定に備えて）

`etl/rules/rulesets.json` にシーズンごとの規則版とフォーマット別の通過人数、`etl/rules/dd_2023-11.json` に DD 表があります。
規則が変わったら新しい版を追加するだけで、大会日から自動で選ばれます。各ランは適用した規則版を持ちます。

## 4. フォルダ

```
etl/            ETL（build.py が入口）
  parsers/      parser_a.py（座標）, parser_b.py（行テキスト）
  rules/        規則版・DD 表
  tests/        変異テスト、レポート要約
  fis_fetch.py  FIS サイトからの取得
  layer5.py     FIS HTML との照合
golden/         目視正解データ
data/           生成物（内容ハッシュ付き JSON と manifest.json）
docs/           実装指示書、検証レポート、自動更新の説明
index.html / athlete.html / about.html / css / js   画面
```
